# News Super Analyser — TG-01.1

## TG-09: автономный единый конвейер

Основная точка входа проекта — [`run.py`](run.py). Она последовательно запускает
существующие этапы: синхронизацию новостей, загрузку полного текста, подготовку
Gemini, предварительный GigaChat-анализ, финальный анализ с созданием объектов и
кадастровое обогащение. Каждый этап выбирает кандидатов из постоянной Google
Таблицы, поэтому обрабатываются и новые, и ранее накопленные строки. Действующие
дедупликация, резервирование TG-07.2 и защита J/O/P/Q сохранены.

Ошибка отдельного этапа включается в итоговую статистику, но не блокирует
независимые последующие этапы. Одновременный цикл в одном процессе запрещён;
дополнительно сервис использует файловую блокировку экземпляра, а окончательную
защиту записей обеспечивают Apps Script `LockService` и существующие ключи.

### Настройка и запуск

Скопируйте `.env.example` в `.env` и заполните существующие настройки Apps
Script/GigaChat, а также:

```dotenv
MANUAL_RUN=true
MONITOR_INTERVAL_MINUTES=60
TELEGRAM_BOT_TOKEN=
TELEGRAM_CHAT_ID=
TELEGRAM_NOTIFICATIONS_ENABLED=true
GOOGLE_SHEET_URL=https://docs.google.com/spreadsheets/d/REPLACE_ME/edit
CADASTRE_MODE=sheets
```

`GOOGLE_SHEET_URL` используется только в уведомлении и не заменяет Apps Script
авторизацию. Если уведомления отключены, токен и chat ID можно оставить
пустыми. Интервал должен быть положительным целым числом.

Для запуска из VS Code откройте `run.py` и нажмите **Run Python File**. Из
терминала используется та же точка входа:

```powershell
python run.py
```

При `MANUAL_RUN=true` выполняется один настоящий цикл и процесс завершается.
При `false` первый цикл начинается немедленно, а каждый следующий — через
`MONITOR_INTERVAL_MINUTES` после полного завершения предыдущего. `Ctrl+C`,
SIGINT и SIGTERM прерывают ожидание и корректно останавливают сервис.

После каждого цикла при включённых уведомлениях отправляется ровно одно
сообщение Telegram со статистикой и постоянной ссылкой на таблицу. Ошибка
Telegram записывается безопасно и не повторяет цикл. Логи выводятся в консоль и
ротируются в `logs/news_super_analyser.log`; токены, общий секрет и ключ
GigaChat проходят централизованное удаление из сообщений. Подробные HTTP-логи
`httpx`, `httpcore`, `urllib3` и `requests` подавлены.

Проверить Telegram-конфигурацию и HTML сообщения без запуска мониторинга и без
сети:

```powershell
python check_telegram.py
```

Только после явного решения отправить одно тестовое сообщение:

```powershell
python check_telegram.py --send
```

При отказе Telegram команда и основной сервис показывают безопасные
`http_status`, `error_code`, описание API и `retry_after`, не выводя токен или
полный Bot API URL. Числовые идентификаторы каналов и супергрупп передаются без
изменения; ограничений по типу чата в приложении нет.

### Docker и Bothost

Репозиторий содержит собственный `Dockerfile` на `python:3.11-slim`. Для
Bothost создайте приложение из проекта, включите **«Использовать собственный
Dockerfile»** и передайте все значения `.env` как переменные окружения панели.
Не копируйте `.env` в образ. Команда контейнера уже задана как `python run.py`,
а `PYTHONUNBUFFERED=1` выводит журнал в панель Bothost. При сборке образ
устанавливает официальные Russian Trusted Root CA и Russian Trusted Sub CA
2024, обновляет системное хранилище Linux и задаёт GigaChat путь к системному
CA bundle. Проверка TLS остаётся обязательной.

Перед реальным размещением отдельно проверьте права Apps Script, постоянную
ссылку таблицы, тестовый Telegram-чат и лимиты GigaChat. Само развёртывание и
реальные внешние вызовы в рамках TG-09 не выполнялись. Контейнер может
перезапускаться: существующая дедупликация таблицы не считает старые новости
новыми. Файловая блокировка защищает один файловый экземпляр; при нескольких
контейнерах на разных хостах окончательной защитой остаётся Apps Script.

### Однократная диагностика НСПД на BotHost

Режим предназначен только для установления уровня сетевого сбоя и не меняет
поиск кадастровых номеров. Он использует ту же команду образа `python run.py`,
поэтому менять команду запуска не нужно. При `NSPD_DIAGNOSTIC_MODE=1` процесс
до чтения рабочей конфигурации выполняет только DNS, TCP, проверенный TLS, один
HTTPS-запрос к корню НСПД, не более одного безопасного GET-запроса к API и
офлайн-проверку конфигурации `pynspd`. Google Sheets, Telegram, Gemini,
GigaChat, основной цикл и планировщик не создаются.

Порядок для панели BotHost без консоли:

1. Остановите бота.
2. Опубликуйте эту версию проекта и дождитесь пересборки Docker-образа.
3. Добавьте переменную `NSPD_DIAGNOSTIC_MODE=1` и запустите бота один раз.
4. Дождитесь `NSPD-DIAG END`, сразу остановите приложение и скопируйте все
   строки от `NSPD-DIAG START` до `NSPD-DIAG END` включительно.
5. Удалите `NSPD_DIAGNOSTIC_MODE` или задайте `0`, примените конфигурацию и
   запустите приложение. Обычный TG-09 возобновится без других изменений.

Пересборка образа обязательна один раз для публикации кода Sprint 003. Для
одного только переключения переменной новая сборка кода технически не нужна:
достаточен перезапуск/повторное развёртывание, которым панель BotHost применяет
окружение. Если панель применяет переменные только при пересборке, используйте
её штатную пересборку.

Диагностика ограничена общим бюджетом 60 секунд, не повторяет HTTP-запросы и
не следует редиректам. Маркер во временной файловой системе не позволяет тому
же контейнеру повторить сетевые запросы после автоматического рестарта. Если
BotHost при каждом рестарте создаёт новый контейнер, временный маркер не
сохраняется; поэтому обязательны остановка до настройки, один контролируемый
запуск и немедленная остановка после `END`. Не оставляйте значение `1` в
штатном развёртывании. Интерпретация полей и технический отчёт приведены в
[`docs/NSPD_DIAGNOSTICS.md`](docs/NSPD_DIAGNOSTICS.md).

Приложение переносит новые строки из листа `ИЖС-КОРП` существующей
Google-таблицы в лист `НОВОСТИ` отдельной приватной таблицы мониторинга.
Python выполняет сравнение, преобразование дат и обработку ошибок, а отдельный
Google Apps Script служит узким авторизованным HTTP-транспортом к двум
таблицам.

Существующие строки назначения не обновляются и не переставляются. Новая
строка определяется по `record_key` и получает статус `Ожидает анализа`.
Листы `АНАЛИЗ` и `ОБЪЕКТЫ` не читаются и не изменяются.

## Как это устроено

Один новый Apps Script предоставляет только три действия:

- чтение значений `ИЖС-КОРП` из исходной таблицы;
- чтение заголовков и `record_key` из `НОВОСТИ`;
- идемпотентное добавление одной строки в `НОВОСТИ`.

Каждый POST-запрос содержит версию протокола, действие, случайный `request_id`
и общий секрет. Скрипт проверяет секрет до доступа к таблицам. Добавление
защищено `LockService`; непосредственно перед записью скрипт снова проверяет
наличие ключа. Поэтому повтор после потерянного HTTP-ответа не создаёт дубль.

## Подключение Apps Script

### 1. Создайте отдельный скрипт

Откройте целевую таблицу `News Super Analyser`, затем выберите
**Расширения → Apps Script**. Это будет новый скрипт анализатора; действующий
Apps Script Telegram-сборщика менять не нужно.

### 2. Вставьте код

Замените содержимое редактора кодом из [apps_script/Code.gs](apps_script/Code.gs)
и сохраните проект.

### 3. Подготовьте таблицы

В исходной таблице должен существовать лист `ИЖС-КОРП` с 11 согласованными
заголовками A:K. В целевой таблице должен существовать лист `НОВОСТИ` с теми
же 11 заголовками и колонкой L `Статус обработки`.

Листы и заголовки скрипт автоматически не создаёт. Перед любой операцией он
проверяет их строго, чтобы не записать данные не в те столбцы.

### 4. Настройте свойства скрипта

Откройте **Настройки проекта → Свойства скрипта** и добавьте:

- `SOURCE_SPREADSHEET_ID` — часть URL исходной таблицы между `/d/` и `/edit`;
- `TARGET_SPREADSHEET_ID` — часть URL целевой таблицы;
- `ANALYSER_SECRET` — отдельная длинная случайная строка.

Аккаунт, от имени которого исполняется скрипт, должен иметь чтение исходной
таблицы и редактирование целевой. Сами таблицы не нужно публиковать или
включать для них доступ по ссылке.

### 5. Разверните веб-приложение

Выберите **Развернуть → Новое развертывание → Веб-приложение**:

- выполнение — от имени владельца скрипта;
- доступ — такой, чтобы локальный Python-клиент мог выполнить POST без
  интерактивного входа (обычно `Все`).

HTTP-точка при этом не отдаёт данные без правильного `ANALYSER_SECRET`.
Считайте URL развёртывания и секрет конфиденциальными. После изменения
`Code.gs` создавайте новую версию развёртывания. Проект ничего не публикует
автоматически.

Скопируйте URL, заканчивающийся на `/exec`.

### 6. Заполните `.env`

```dotenv
GOOGLE_APPS_SCRIPT_URL=https://script.google.com/macros/s/REPLACE_ME/exec
GOOGLE_APPS_SCRIPT_SECRET=тот_же_секрет_что_в_ANALYSER_SECRET
```

`.env`, локальные журналы и JSON-файлы исключены из Git. Секрет не включается

### 7. Выполните первую синхронизацию


Постоянный режим с интервалом из `SYNC_INTERVAL_MINUTES`:

```powershell
python -m news_super_analyser schedule
```

Остановка — `Ctrl+C`.

## Sprint 001: Telegram Full Text

Контур полного текста отделён от TG-01. Существующая синхронизация продолжает
работать только с A:L, а ручной обработчик Telegram использует только:

- M — `Полный текст`;
- N — `Статус загрузки`;
- O — `Дата загрузки`.

Эти три заголовка нужно добавить в уже существующий лист `НОВОСТИ` вручную и
именно справа от L. Код не создаёт и не переставляет колонки. Перед каждой
операцией Apps Script отдельно проверяет A:L и M:O.

`read_full_text_candidates` возвращает не более 20 строк, у которых все три
ячейки M:O пусты. Через HTTP передаются `record_key`, содержимое колонки
`Ссылки` и исходный текст F. `update_full_text` повторно находит строку по `record_key`
под `LockService` и записывает исключительно M:O. Номер строки от Python не
принимается. Если хотя бы одна из M:O уже заполнена, возвращается
`already_processed` и данные пользователя не изменяются.

Статусы колонки N:

- `Загружено` — embed-текст получен; O содержит время UTC+05:00;
- `Недоступно` — публикация или текстовый контейнер недоступны;
- `Неподдерживаемая ссылка` — нет поддерживаемой публичной ссылки `t.me`;
- `Ошибка` — тайм-аут, ограничение частоты, неожиданный HTTP-ответ или слишком
  длинный текст.

При неуспешном извлечении статус N сохраняет фактический результат попытки, а
O остаётся пустой. Если F содержит пригодный исходный текст, он записывается в
M без изменения статуса N; если F пустая, M также остаётся пустой. Запись с
заполненной N не повторяется автоматически. Для осознанного повтора
пользователь должен очистить M:O этой строки вручную.

### Подготовка и ручной запуск одной записи

1. Добавьте точные заголовки M:O, предварительно сохранив резервную копию
   таблицы.
2. Вставьте актуальный [apps_script/Code.gs](apps_script/Code.gs) в проект
   Apps Script и создайте новую версию веб-развёртывания.
3. Проверьте `GOOGLE_APPS_SCRIPT_URL` и секрет в `.env`.
4. Запустите явно:

```powershell
python -m news_super_analyser.full_text_cli --limit 1 --request-delay 1 --apply
```

Без `--apply` команда ничего не читает и не записывает. Ожидаемый итоговый
вывод имеет вид:

```text
TG-02A: кандидатов=1, получено текстов=1, ошибок загрузки=0, обновлено=1, уже обработано=0, не найдено=0, ошибок записи=0
```

Запуск остаётся только ручным: scheduler и массовая обработка не добавлены.
Полный текст не выводится в консоль и журнал.

### Ограничения Telegram embed

- Поддерживаются только HTTPS-ссылки публичных публикаций вида
  `t.me/<channel>/<message_id>` и `t.me/s/<channel>/<message_id>`.
- Пользовательская Telegram-сессия, Bot API и MTProto не используются.
- Приватные, удалённые, ограниченные и требующие входа публикации недоступны.
- Telegram может изменить HTML embed или ограничить частоту запросов.
- Клиент использует тайм-аут из `HTTP_TIMEOUT_SECONDS`, выполняет запросы
  последовательно и выдерживает настраиваемую паузу, по умолчанию одну секунду.
- Извлекается только `tgme_widget_message_text`, поэтому реакции, просмотры и
  интерфейс Telegram не попадают в M. Авторские подписи и ссылки внутри тела
  самой публикации сохраняются.

## TG-04: единый источник текста и безопасный backfill

Колонка M `Полный текст` является единственным источником входа GigaChat.
Анализатор больше не читает F и не обращается к Telegram для резервного
получения текста. Если M пустая или содержит только пробелы, попытка завершается
диагностической ошибкой `Полный текст отсутствует в колонке M` без вызова
модели.

Для ранее загруженных строк добавлена отдельная ручная операция backfill. Она
на стороне Apps Script повторно находит строку по `record_key`, читает F и
записывает только пустую M. Существующая M никогда не перезаписывается; пустая
или пробельная F пропускается. Колонки L, N и O, а также листы `АНАЛИЗ`,
`ОБЪЕКТЫ` и `ИИ_ОТВЕТЫ` не читаются для принятия решения и не изменяются.
Операция не создаёт Telegram-клиент, не обращается к ИИ и не инициирует анализ.
Повторный вызов для уже заполненной строки возвращает `already_processed`.

После публикации актуальной версии Apps Script и отдельного разрешения на
рабочую таблицу backfill небольшой порции запускается вручную:

```powershell
python -m news_super_analyser.full_text_cli --limit 20 --backfill-source-text --apply
```

Без `--apply` чтение и запись не выполняются. Команда в рамках разработки
TG-04 не запускалась на рабочей таблице.

## TG-05: подготовка формул Gemini

Колонка P листа `НОВОСТИ` имеет заголовок `Джемини`. Она используется только
для нативной формулы Google Таблиц `=AI()` и не входит в автоматический контур
GigaChat. Код не создаёт колонку: заголовок P нужно добавить вручную справа от
O. Проверки A:L и M:O остаются без изменений, поэтому TG-01, TG-02A и TG-04 не
перезаписывают P.

Кандидатом считается строка с непустой M и полностью свободной P. Apps Script
находит её по `record_key`, повторно проверяет M и проверяет как значение, так
и формулу в P. Непустая P никогда не перезаписывается, включая ещё не
сгенерированную формулу и готовый ручной результат. Записывается формула со
ссылкой на M той же фактической строки, например:

```text
=AI("<English prompt>";M17)
```

Английский промпт просит вернуть структурированный обычный текст на русском,
не JSON: тип происшествия, краткую сводку, все затронутые объекты, их тип,
собственника или ответственную организацию, адрес или ориентир, кадастровый
номер, повреждения и короткие подтверждающие цитаты. Неуказанные сведения
должны быть явно отмечены; придумывать факты и использовать внешние сведения
запрещено.

Безопасный просмотр одной согласованной строки ничего не записывает:

```powershell
python -m news_super_analyser.gemini_formula_cli --dry-run --limit 1 --record-key "-100:123"
```

После отдельного подтверждения формула для этой же строки подготавливается так:

```powershell
python -m news_super_analyser.gemini_formula_cli --apply --limit 1 --record-key "-100:123"
```

Команда только помещает формулу в P. Генерация Gemini автоматически не
запускается: пользователь выбирает ячейку и нажимает «Сгенерировать и
заполнить» в интерфейсе Google Таблиц. Массовая подготовка формул не добавлена
в scheduler и требует отдельного подтверждения.

## TG-06: структурированный текст GigaChat в Q

Колонка Q листа `НОВОСТИ` имеет заголовок `Гига`. Это отдельный ручной этап,
который не заменяет и не изменяет существующий JSON-анализатор TG-02B/TG-03.
Единственный источник новости — непустая M `Полный текст`; F, ссылки и ответы
Gemini не используются.

Apps Script выбирает строки с непустой M и полностью пустой Q. Python получает
строку по `record_key`, выполняет существующую консервативную нормализацию и
отправляет её через действующий OAuth/HTTP-клиент GigaChat. Для этого режима
JSON Schema принудительно отключена независимо от значения
`GIGACHAT_STRUCTURED_OUTPUT`.

Промпт требует обычный структурированный текст на русском: тип происшествия,
краткую сводку и все упомянутые физические объекты, включая неповреждённые.
Для каждого объекта запрашиваются название, тип, организация или собственник,
регион, населённый пункт, точный адрес, кадастровый номер, повреждения,
количество и короткая точная цитата. Неизвестные значения обозначаются
`Не указано`; JSON и Markdown code blocks не принимаются.

Перед записью Apps Script под блокировкой повторно находит строку по
`record_key`, проверяет M и проверяет как значение, так и формулу Q. Запись
выполняется только в Q. Непустая Q возвращает `already_processed` и никогда не
перезаписывается. M–P, `АНАЛИЗ`, `ОБЪЕКТЫ` и `ИИ_ОТВЕТЫ` не изменяются этим
этапом.

При HTTP/API-ошибке, тайм-ауте, blacklist, пустом, неполном, JSON- или
code-fence-ответе Q остаётся пустой, а безопасная диагностика попадает только
в локальный журнал. Временные ошибки используют существующую ограниченную
политику повторов; запись выполняется один раз после успешного ответа.

Безопасный просмотр одной согласованной строки не вызывает модель и не пишет:

```powershell
python -m news_super_analyser.giga_text_cli --dry-run --limit 1 --record-key "-100:123"
```

После отдельного разрешения один анализ запускается вручную:

```powershell
python -m news_super_analyser.giga_text_cli --apply --limit 1 --record-key "-100:123"
```

Колонку Q с точным заголовком `Гига` нужно добавить вручную справа от P и
опубликовать актуальный Apps Script. Новый этап не включён в scheduler.

## TG-07: финальный анализ готовых ответов P/Q

Активный маршрут записи итоговых данных теперь выглядит так:

```text
НОВОСТИ (готовый P + необязательный Q) → финальный GigaChat JSON → АНАЛИЗ + ОБЪЕКТЫ
```

Прямая отправка M в финальный JSON-анализатор удалена. M по-прежнему служит
единственным источником для подготовительных этапов TG-05 и TG-06, но финальная
модель обязательно получает готовый ответ Gemini из P и, при наличии, готовый
ответ первичного GigaChat из Q. Формула P без рассчитанного ответа,
ошибка формулы, одиночный `-`, служебное состояние или пустая P/Q не считаются
готовым ответом. Apps
Script проверяет одновременно фактическое отображаемое значение и формулу
ячейки, а не только первый символ текста.

Финальный анализ запускается только после готовности Gemini. Если Q отсутствует,
он выполняется по одному P; если Q готов, оба ответа передаются с явными метками
`[Gemini]` и `[GigaChat]` для сопоставления. Готовый Q без P не допускает строку
к финальному анализу: она остаётся в `Ожидает анализа` до следующего запуска.
Финальный промпт требует объединить одинаковые объекты, сохранить
противоречия в `Примечание ИИ`, не повышать неподтверждённые утверждения до
фактов и хранить групповое количество одной записью, а не создавать фиктивные
объекты.

Колонка `Модель` листа `ОБЪЕКТЫ` содержит фактическое происхождение входов:
`Gemini`, `GigaChat` или `Gemini + GigaChat`. В `АНАЛИЗ` модель остаётся
`GigaChat`, поскольку именно она выполняет финальное структурирование. Схемы и
порядок колонок всех листов не менялись.

Успешный результат определяется не только строкой `АНАЛИЗ`: Apps Script также
сверяет `Количество объектов` с фактическим числом связанных строк
`ОБЪЕКТЫ`. Межлистовая операция выполняется под одной блокировкой и повторно
дописывает только отсутствующие номера объектов. Потеря ответа между листами
не создаёт дубль и не позволяет пометить неполную запись завершённой. Анализ с
нулём объектов считается завершённым при нулевом числе строк `ОБЪЕКТЫ`.

После успешного результата повторный вызов модели запрещён. Для ошибки повтор
возможен только после ручного возврата L в `Ожидает анализа`.

### TG-07.1: дата новости в ОБЪЕКТЫ

Лист `ОБЪЕКТЫ` расширен колонкой N с точным заголовком
`Дата и время новости`. Для каждой новой строки объекта используется исходное
`news_datetime` той же новости, которое записывается в колонку C листа
`АНАЛИЗ`. Время обработки для этого поля не используется.

Исходные даты проекта нормализованы в часовом поясе UTC+5
(`Asia/Yekaterinburg`). Apps Script проверяет формат `dd.MM.yyyy HH:mm:ss`,
записывает N как числовую дату Google Sheets и применяет такой же формат
отображения. Поэтому колонка пригодна для сортировки и фильтрации по диапазону.
Пустая исходная дата остаётся пустой. Колонки A–M не преобразуются и не
перезаписываются.

Перед публикацией обновлённого Apps Script необходимо вручную добавить в
существующий лист `ОБЪЕКТЫ` колонку N с заголовком `Дата и время новости`.
Скрипт проверяет контракт и не создаёт колонку автоматически. Автоматический
backfill старых строк в TG-07.1 не выполняется.

## TG-02B/TG-03: финальный анализ через GigaChat

Это отдельный ручной этап, не включённый в scheduler. Он не меняет A:Q листа
`НОВОСТИ`, кроме существующего управления очередью через L. Обычный запуск
выбирает ожидающую строку с готовым P и необязательным готовым Q, для которой ещё нет полного
успешного анализа. Ошибочную попытку можно повторить после ручного возврата L
в очередь; принудительный повтор успешного результата не предусмотрен.

Протокол состоит из четырёх защищённых операций Apps Script:

1. Выбор и атомарное резервирование небольшой порции из `НОВОСТИ`.
2. Идемпотентное сохранение исходного ответа в `ИИ_ОТВЕТЫ`.
3. Идемпотентное сохранение общей строки и объектов по одному `ID анализа`.
4. Условная фиксация итогового статуса L по токену резерва.

Исходный финальный ответ сохраняется до разбора JSON. При невалидном JSON он остаётся в
`ИИ_ОТВЕТЫ`, ошибка дописывается отдельной условной операцией, а `АНАЛИЗ`
получает статус `Ошибка`. После неоднозначного сбоя повтор той же серверной
операции дописывает только недостающие строки. Apps Script сверяет точные
заголовки и не создаёт листы автоматически.

### Точные заголовки листов

`АНАЛИЗ` (A:M):

```text
ID анализа | record_key | Дата и время новости | Ссылка на новость | Модель | Статус анализа | Тип происшествия | Регион | Населённый пункт | Краткое описание | Количество объектов | Текст на английском | Дата и время анализа
```

`ОБЪЕКТЫ` (A:N):

```text
ID анализа | Номер объекта | Модель | Название объекта | Тип объекта | Организация | Регион | Населённый пункт | Адрес / ориентир | Кадастровый номер | Повреждения | Подтверждающий фрагмент | Примечание ИИ | Дата и время новости
```

`ИИ_ОТВЕТЫ` (A:F):

```text
ID анализа | Модель | Дата и время запроса | Входной текст | Полный ответ модели | Ошибка
```

### Настройка

Добавьте в локальный `.env` ключ авторизации GigaChat. Значения по умолчанию
соответствуют минимальной интеграции, используемой в проекте:

```dotenv
GIGACHAT_AUTH_KEY=ваш_ключ_авторизации
GIGACHAT_SCOPE=GIGACHAT_API_PERS
GIGACHAT_MODEL=GigaChat-3-Ultra
GIGACHAT_TIMEOUT_SECONDS=90
GIGACHAT_STRUCTURED_OUTPUT=false
GIGACHAT_CA_BUNDLE=
```

`truststore` подключает системное хранилище сертификатов только к отдельной
HTTP-сессии GigaChat. В Docker `GIGACHAT_CA_BUNDLE` уже указывает на системный
Linux bundle, дополненный официальной цепочкой НУЦ Минцифры. При локальном
запуске переменная по умолчанию пуста и продолжает использоваться системное
хранилище Windows. Глобальная подмена `ssl` не выполняется, поэтому Google
transport TG-01/TG-02A не меняется. Отключение проверки TLS не предусмотрено.
После замены `Code.gs` опубликуйте новую версию существующего веб-приложения.

`GIGACHAT_STRUCTURED_OUTPUT=true` включает JSON Schema для существующего
контракта `incident_type`, `region`, `locality`, `summary`, `objects`. Режим
опционален: значение `false` сохраняет прежний запрос и совместимость. Nullable
поля в схеме допускают строку либо `null`; формат листов не меняется.

### Диагностика HTTP 404 от 27.10.2026

Фактический production-путь эталонного проекта прослежен как
`monitoring_pipeline_v2.py` → `discovery_second_pass.py` →
`raccoon_scout_sprint005/analyzer.py`. Он использует OAuth
`https://ngw.devices.sberbank.ru:9443/api/v2/oauth`, Chat API
`https://api.giga.chat/v1/chat/completions`, scope `GIGACHAT_API_PERS` и модель
`GigaChat-3-Ultra` из `config.py`. Сохранённые результаты эталонного проекта за
25–26 октября также указывают `GigaChat-3-Ultra`.

| Компонент | Эталонный production-путь | TG-02B до исправления | После исправления |
|---|---|---|---|
| OAuth URL | `ngw.devices.sberbank.ru:9443/api/v2/oauth` | тот же | тот же |
| Chat URL | `api.giga.chat/v1/chat/completions` | тот же | тот же |
| Метод | POST | POST | POST |
| Заголовки | Bearer, JSON | Bearer, JSON | Bearer, JSON, Accept JSON |
| Модель | `GigaChat-3-Ultra` из `config.py` | фактически `GigaChat` при пустом env | `GigaChat-3-Ultra` из единой константы/env |
| Тело | model, temperature, messages | те же обязательные поля | без изменения контракта |
| SSL | стандартная проверка Python | глобальный `truststore.inject_into_ssl()` | отдельная truststore-сессия |
| HTTP-ошибка | полный exception urllib | только статус | статус, URL, модель и очищенные поля ответа |

Причина одинакового 404 после правок значения в dataclass была в двух
независимых значениях по умолчанию: `GigaChatSettings.model` уже содержал
`GigaChat-3-Ultra`, но `from_env()` при отсутствии `GIGACHAT_MODEL` всегда
создавал настройки с `GigaChat`. Именно это значение попадало в JSON. Согласно
официальной справке GigaChat, HTTP 404 метода Chat означает неверный
идентификатор модели. Теперь значение по умолчанию одно, а CLI перед запросом
безопасно показывает фактические URL и модель.

Старый endpoint `gigachat.devices.sberbank.ru` найден только в неиспользуемой
копии `analyzer11.py`; переключение на него не требуется. Корневой `monitor.py`
— отдельный эксперимент с `verify=False`, он не входит в production-путь и не
использовался как образец исправления.

При HTTP 400/401/403/404/429/500 клиент включает в ошибку только короткие поля
`code`, `status`, `message`, `error`, `detail`. Заголовки Authorization, токены,
ключи, входной текст и полный ответ сервера не выводятся.


Первый реальный тест одной новости:


Конкретная запись:

## TG-03: очередь ИИ-анализа

Колонка L листа `НОВОСТИ` теперь является очередью текущего запланированного
анализа:

| Статус | Поведение |
|---|---|
| `Ожидает анализа` | доступно обычному запуску |
| `В обработке` | зарезервировано выполняющим процессом |
| `Обработано` | успешный результат подтверждён в `АНАЛИЗ` |
| `Ошибка анализа` | попытка завершена ошибкой; автоматически не повторяется |
| `Пропущено` | ручное исключение из финального анализа |

TG-01 устанавливает `Ожидает анализа` только новой строке. Существующие строки
он не обновляет, поэтому ручные и служебные статусы не сбрасываются. Обычная
выборка берёт только `Ожидает анализа` и дополнительно исключает `record_key`,
для которого уже есть успешная строка `GigaChat` в `АНАЛИЗ`. При запуске с
записью Apps Script под блокировкой переводит L в `В обработке` и создаёт
двухчасовую аренду с одноразовым токеном. Другой процесс не может получить ту
же запись. Просроченная аренда автоматически возвращает запись в выборку, так
что прерванная обработка не зависает навсегда.

Статус `Обработано` устанавливается только после подтверждённого сохранения
успешного анализа. Любая ошибка конкретной новости переводит её в
`Ошибка анализа`, не останавливая следующую запись партии. Чтобы повторить
ошибочную новость, вручную верните L в `Ожидает анализа`; прежние строки
`ИИ_ОТВЕТЫ` и `АНАЛИЗ` сохраняются. Если успешный анализ уже существует, новый
не создаётся, а при рабочем запуске неверный статус безопасно восстанавливается
в `Обработано`.

Источники финальной модели — готовый отображаемый результат P и необязательный
готовый Q. Формула P без готового результата и одиночный `-` игнорируются.
Без готового P новость не резервируется, сохраняет `Ожидает анализа`, а модель
не вызывается независимо от Q. При готовом P пустая Q не мешает анализу по
Gemini. Ожидающая строка не блокирует следующие новости. M, F и Telegram
финальным анализатором не читаются.

GigaChat теперь классифицируется по структурному `finish_reason`:
`blacklist` записывается как тематическое ограничение, другие незавершённые
причины — как неполный ответ. Исходный ответ провайдера сохраняется в
`ИИ_ОТВЕТЫ`, если он был получен; отказ не превращается в успешный результат с
нулём объектов. Некорректный JSON, HTTP/API, соединение и ошибки записи имеют
отдельные понятные причины. Секреты в диагностику не включаются.

Безопасная ручная проверка сначала без GigaChat и без записи:

```powershell
python -m news_super_analyser.ai_analysis_cli --limit 1 --dry-run
```

После проверки кандидата — одна или две последовательные новости:

```powershell
python -m news_super_analyser.ai_analysis_cli --limit 1 --apply
python -m news_super_analyser.ai_analysis_cli --limit 2 --apply
```

Команды `--apply` обращаются к Google Sheets и GigaChat, поэтому в рамках
разработки они автоматически не запускались. Telegram embed используется
только отдельным этапом TG-02A до анализа.
Многомодельный scheduler не добавлен. Дедупликация финального результата
выполняется по `record_key`; появление второго ответа после успеха не запускает
повторный платный анализ.

### TG-03.1: нормализация подготовительного текста

Перед запросом TG-06 текст M проходит консервативную нормализацию. Она удаляет
пустые строки, невидимые символы, лишние пробелы,
точно распознанные навигационные строки наподобие
`VK | Одноклассники | MAX | Telegram`, короткие технические подписи и повтор
одинакового заголовка. Фильтрация применяется только к целым строкам и не
удаляет строку из-за одного слова `Telegram`, `MAX` или другого совпадения.
Первая содержательная строка сохраняется, как и сведения о происшествиях,
объектах, адресах, населённых пунктах и повреждениях.

Оригинальная публикация в M не изменяется. Финальный этап TG-07 повторно не
нормализует готовые ответы P/Q; в поле `Входной текст` листа `ИИ_ОТВЕТЫ`
сохраняются фактически переданные ответы с метками их источников.

Временные ошибки соединения, HTTP 429 и HTTP 5xx повторяются не более трёх раз
с существующей ограниченной задержкой. Запись в `ИИ_ОТВЕТЫ`, `АНАЛИЗ` и
`ОБЪЕКТЫ` начинается только после окончания этих попыток, поэтому сетевой
повтор не создаёт строк-дубликатов. HTTP 4xx, ошибки формата и тематический
`finish_reason=blacklist` повторно не отправляются. При `blacklist` одна и та
же попытка сохраняет свой `ID анализа`, исходный ответ провайдера и понятную
причину отказа в существующем `ИИ_ОТВЕТЫ`; изменённый текст автоматически не
формируется и не отправляется.

### Ошибки и ограничения TG-02B

- Финальное структурирование использует только GigaChat REST API. Готовый
  результат Gemini обязателен и при наличии сопоставляется с готовым
  результатом первичного GigaChat; внешний поиск и дополнение фактов не
  выполняются.
- Клиент выполняет один логический запрос. Только временный транспортный сбой,
  HTTP 429 или 5xx допускает до трёх попыток; остальные ошибки не повторяются.
- JSON проверяется структурно. В прежнем режиме отсутствующие поля сохраняются
  как пустые ячейки; строгий JSON Schema требует все поля, но разрешает `null`.
- Текст или ответ длиннее 50 000 символов не обрезается: полные данные
  сохраняются локально в `data/ai_responses/<ID анализа>.json`, а в таблице
  остаётся понятная диагностика. Каталог исключён из Git.
- Локальный резервный файл может содержать полный текст новости и ответ модели;
  его следует защищать как рабочие данные и удалять по принятой политике.
- Автоматическое расписание и массовый режим не добавлены.


Python-тесты используют имитации HTTP и Google Sheets. JavaScript-harness

## Надёжность и ограничения

- При каждом цикле заново читаются ключи назначения; курсор последней строки
  не используется.
- После неоднозначной ошибки записи Python перечитывает ключи. Если сверка
  недоступна, повторная запись в этом цикле не выполняется; следующий цикл
  безопасно разрешит состояние.
- Чтения и временные HTTP-ошибки имеют ограниченные повторы с задержкой;
  числовой `Retry-After` учитывается.
- Даты с часовым поясом переводятся в UTC+05:00. Некорректная дата сохраняется
  исходной строкой и отмечается предупреждением.
- Значения, похожие на формулы, сохраняются как текст. Ячейка длиннее лимита
  Google Sheets в 50 000 символов отклоняется без молчаливого обрезания.
- Внутри Python-процесса параллельный запуск блокируется, а записи Apps Script
  сериализуются через `LockService`. Координации нескольких Python-процессов
  нет, но серверная дедупликация сохраняет идемпотентность.
- Каждый цикл передаёт через Apps Script весь используемый диапазон источника.
  Для очень больших таблиц могут потребоваться пакетное чтение или иной
  транспорт в будущем.
- Если политика Google Workspace запрещает веб-приложения без интерактивного
  входа, схема с общим секретом потребует согласования с администратором.

# TG-08: кадастровое обогащение листа «ОБЪЕКТЫ»

TG-08 можно запускать отдельно вручную; в режиме `CADASTRE_MODE=direct` TG-09
также вызывает его последним этапом перед итоговым Telegram-отчётом. Он читает строки листа `ОБЪЕКТЫ`, ищет
публичные кадастровые сведения через библиотеку `pynspd` и подготавливает
нативную формулу Google Sheets `=AI()`. GigaChat и Gemini API из Python не
вызываются.

Лист должен сохранять базовые A:N TG-07 и иметь точные заголовки:

- O — `Кадастровый квартал`;
- P — `Все кадастровые`;
- Q — `Джемини`.

Код не создаёт, не перемещает и не переименовывает колонки. После добавления
заголовков нужно опубликовать новую версию `apps_script/Code.gs`. Новые строки
TG-07 записываются в A:N, а O:Q остаются пустыми.

## Правила заполнения

Каждая из J, O, P и Q обрабатывается независимо. Любое существующее содержимое
считается ручным и не меняется: текст, число, формула, результат формулы и
символ `-`. Непосредственно перед записью Apps Script под блокировкой повторно
находит объект по паре `ID анализа` + `Номер объекта` и ещё раз проверяет
целевую ячейку. Очищенная пользователем ячейка снова становится доступной при
следующем запуске.

Адресный поиск выполняется только при наличии населённого пункта и достаточно
конкретного адреса с улицей/территорией и номером дома. Запрос формируется из
G/H/I. Результаты консервативно проверяются по населённому пункту, региону,
улице, дому, а при наличии — корпусу и строению.

- J заполняется только при одном уникальном полном кадастровом номере;
- O заполняется только при одном квартале либо извлекается из уже известной J;
- P содержит все уникальные подходящие полные номера через перенос строки;
- Q получает `=AI()` только при наличии города и организации F или объекта D.

Если J уже содержит корректный полный номер, O и пустая P формируются из J
локально, без НСПД. Ручные непустые значения по-прежнему не заменяются.

Если совпадения неоднозначны, J остаётся пустой. Если номера относятся к
разным кварталам, O остаётся пустой. Ошибка одной строки не останавливает
остальные; незаполненные поля будут проверены повторно при следующем запуске.

## Безопасный запуск

Установите зависимости и сначала проверьте одну согласованную строку без
записи:

```powershell
python -m pip install -r requirements-dev.txt
python -m news_super_analyser.cadastral_enrichment_cli --dry-run --row 2 --limit 1 --request-delay 1
```

После просмотра результата и отдельного разрешения на приёмку одной строки:

```powershell
python -m news_super_analyser.cadastral_enrichment_cli --apply --row 2 --limit 1 --request-delay 1
```

Для всех подходящих строк можно опустить `--row` и выбрать `--limit` от 1 до
500. Массовый `--apply` следует запускать только после отдельного согласования.

Рекомендуемые настройки Docker/BotHost:

```dotenv
NSPD_CLIENT_TIMEOUT=10
NSPD_ROW_TIMEOUT_SECONDS=30
NSPD_STAGE_TIMEOUT_SECONDS=120
NSPD_ATTEMPTS=2
NSPD_REQUEST_DELAY_SECONDS=1
```

`NSPD_CLIENT_TIMEOUT` теперь является жёстким wall-clock лимитом одного
изолированного процесса запроса. При превышении процесс завершается, поэтому
зависших потоков не остаётся. Внутренние повторы `pynspd` и `httpx` отключены;
единственный управляемый retry выполняет проект, не более `NSPD_ATTEMPTS` раз.
Переменные `PYNSPD_CLIENT_TIMEOUT` и `PYNSPD_CLIENT_RETRIES` игнорируются и не
требуются. Максимум строки — 30 секунд, планирование новых запросов этапа
прекращается через 120 секунд; оставшиеся строки откладываются до следующего
цикла, после чего TG-09 формирует частичный Telegram-отчёт.

Для ручного CLI значения можно временно переопределить флагами
`--http-timeout`, `--row-timeout`, `--stage-timeout`, `--nspd-attempts` и
`--request-delay`.

Рабочий процесс `pynspd` использует системное хранилище CA с обязательной
проверкой сертификата и hostname. Непроверяемый SSL-контекст библиотеки в
рабочем пути не используется; Docker уже содержит официальную российскую
цепочку доверия.

`--dry-run` читает таблицу и может обращаться к публичной НСПД, но ничего не
записывает. Формула Q использует тот же рабочий двухаргументный синтаксис
`=AI("prompt";data)`, что и существующий этап Gemini; результат автоматически
не переносится в I.

## TG-08.1: английский Gemini-промпт и каскад НСПД

После реальной приёмки инструкция Q заменена на английскую, поскольку Google
Sheets AI отклонял русский язык. Формула сохраняет диапазон текущей строки,
например `=AI("<English prompt>";D3:I3)`. Она просит предпочесть организацию F,
иначе объект D, учитывать город H и регион G и вернуть только адрес,
предпочтительно на русском. Существующая непустая Q, включая старую формулу или
ошибку, не заменяется; новую формулу можно получить, только очистив Q вручную.

Кадастровый поиск теперь использует не более трёх уникальных вариантов:

1. исходные G + H + I;
2. нормализованный адрес без повторов географии и с едиными обозначениями;
3. расширенный запрос по региону/городу, улице и дому без корпуса/строения.

Каждый кандидат любого уровня всё равно проверяется по исходному полному
адресу. Поэтому результат третьего уровня без подтверждения исходного корпуса
или строения автоматически не принимается. Каскад останавливается после первого
уровня с достоверными совпадениями. Эквивалентные запросы повторно не
отправляются.

Примеры нормализации:

```text
Москва, Москва, Профсоюзная улица, дом 123А, строение 15
→ москва профсоюзная 123а строение 15

г. Москва, ул. Профсоюзная, д. 123А, стр. 15
→ москва профсоюзная 123а строение 15
```

CLI печатает для каждой строки уровень, безопасное представление запроса,
фактическое число попыток, число кандидатов НСПД, принятые и отклонённые
кандидаты, причины отклонения и итог. Статусы `empty`, `all_rejected`,
`nspd_unavailable`, `response_error` и `matched` различаются. При массовой
обработке вывод ограничен максимум тремя логическими уровнями на строку.

Повторная безопасная проверка строки 3:

```powershell
python -m news_super_analyser.cadastral_enrichment_cli --dry-run --row 3 --limit 1 --request-delay 1
```

### TG-08.2: подробности отклонённых кандидатов

Обычный вывод по-прежнему содержит только агрегированные причины. Для
исследования расхождений НСПД можно явно включить подробности первых пяти
отклонённых кандидатов на строку:

```powershell
python -m news_super_analyser.cadastral_enrichment_cli --dry-run --row 3 --limit 1 --request-delay 1 --diagnostic-rejections
```

Для каждого образца выводятся исходный публичный адрес НСПД, нормализованные
адреса кандидата и источника, причина отклонения и фактически сравниваемые
улица, дом и строение. Флаг не меняет правила сопоставления и не влияет на
J/O/P. Без `--diagnostic-rejections` подробные адреса не сохраняются в
диагностической модели и не печатаются. `--dry-run` ничего не записывает в
Google Таблицу.

### TG-08.3: явное извлечение улицы

Парсер улицы не использует административное сокращение `тер.` как дорожный
маркер. В длинных адресах НСПД он ищет явные типы — `ул.`, улица, проспект,
`пр-т`, переулок, `пер.`, шоссе, бульвар, проезд и другие — до или после
названия. Компоненты `вн.тер.г.`, муниципальный округ, район, город, область и
Российская Федерация улицей не считаются. Если явный тип не найден, парсер не
угадывает улицу и кандидат отклоняется по прежней безопасной логике.

## Гибридное кадастровое обогащение

По умолчанию `CADASTRE_MODE=sheets`: Bot 2 не обращается к НСПД, а последним
этапом синхронизирует лист `КАДАСТРЫ`. Для временного возврата прежнего
механизма задайте `CADASTRE_MODE=direct` и перезапустите процесс. Неизвестное
значение завершает запуск ошибкой конфигурации; автоматического переключения
между режимами нет.

Лист `КАДАСТРЫ` создаётся вручную с точными колонками A:J:

```text
ID объекта | Регион | Населённый пункт | Адрес | Кадастровый номер |
Кадастровый квартал | Все кадастровые номера | Статус | Ошибка | Дата проверки
```

Сначала опубликуйте новую версию `apps_script/Code.gs` как существующее
веб-приложение, не меняя Script Properties и URL `/exec`. Затем обновите код
BotHost и установите `CADASTRE_MODE=sheets`.

Локальный проход на Windows использует те же `GOOGLE_APPS_SCRIPT_URL`,
`GOOGLE_APPS_SCRIPT_SECRET` и настройки `NSPD_*` из корневого `.env`:

```powershell
python -m news_super_analyser.cadastral_queue_cli
```

Один запуск получает текущий снимок строк `ОЖИДАЕТ` и `ОШИБКА`, последовательно
обрабатывает его и завершается. Локальный журнал сохраняется в
`logs/cadastral_queue_local.log`. Скрипт не читает `ОБЪЕКТЫ`; Apps Script
условно принимает результат только при неизменных ID, регионе, населённом
пункте и адресе.
